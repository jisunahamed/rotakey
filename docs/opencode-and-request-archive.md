# OpenCode routing and daily request archive

Providers configured with `https://opencode.ai/zen/v1` use the private OpenCode sidecar for model discovery, provider validation and inference. The provider editor's **Use OpenCode free proxy** preset fills this address. Add `public` as the credential for the free tier and publish the desired models. OpenAI, Responses and Anthropic callers use Rotakey's existing translation and admission system. Unrelated providers are not redirected. The sidecar is pinned to the contract/catalog from `bigdata2211it-web/opencode-free-proxy` revision `49488fd2c6623cbcfdf11ef584722563df08aceb`.

Start the sidecar with `docker compose --profile opencode up -d opencode-proxy`. Configure `OPENCODE_PROXY_URL=http://opencode-proxy:6446` and a matching random `OPENCODE_PROXY_KEY` in the app environment. The service has no public host port and prints no keys. OpenCode calls fail closed if the sidecar is not configured. The proxy preserves the full JSON body, status, error replies and stream bytes; it cancels upstream work when the caller disconnects.

In **System settings → Save all request data**, On records the complete received input and forwarded output for every inference model, including streamed replies and errors, encrypted in the VPS database. Global capture bypasses the old per-route capture byte ceiling. Turning it off restores per-route capture preferences and does not erase existing data. It captures application payloads, not authentication headers. It cannot reconstruct bodies that were never saved, bytes never received from the client/provider or output that could not be delivered.

The archive is independent of this switch: all saved request records, including metadata-only rows, are eligible. Configure `REQUEST_ARCHIVE_ENABLED=true` to prevent ordinary request retention from removing data before archival. Provider/model/key settings, account balances and other application tables remain local.

`rotakey-archive.timer` runs at **00:00 Asia/Dhaka** every day; `Persistent=true` runs a missed scheduled transfer after startup. The service retries failures after five minutes. The first transfer can be started with `systemctl start --no-block rotakey-archive.service`. Inspect progress with `journalctl -u rotakey-archive.service` and the next run with `systemctl list-timers rotakey-archive.timer`.

The root-only `/opt/rotakey/.archive.env` contains `DATABASE_URL` for the source, `APP_MASTER_KEY`, `ARCHIVE_DATABASE_URL` and a stable `ARCHIVE_INSTANCE_ID`. These credentials never belong in Git, the admin settings JSON or a public frontend. The remote connection requires verified TLS. Only `rotakey_archive.requests` and `rotakey_archive.runs` are created. Row-level security is enabled without public access policies; use the Supabase SQL editor/authorized database role to read them.

Each batch is copied to a transaction-local staging table, merged idempotently by instance/request ID, compared against the staged input/output and metadata, and committed. Only then are unchanged source rows deleted. A source row fingerprint prevents a concurrent edit from being deleted. Copy/decryption/verification/commit failure leaves that batch on the VPS. A process crash after remote commit can safely repeat the transfer. Existing input/output is decrypted into the access-controlled remote archive, while legacy truncated or absent bodies remain explicitly marked in metadata.

Archived records no longer appear in the VPS request explorer or its history-derived charts. They remain in Supabase. New connected requests continue normally during archival. The transfer never replays a model request or exports provider/API-key secrets. Raw input/output may contain sensitive user content, so access to the private archive remains an administrator responsibility.

Verification covers switch persistence, full response capture, private proxy routing and secret replacement, status/body preservation, cancellation without replay, idempotent archival, concurrent source changes and keeping source data on remote/decryption failure. Deployment must also verify the compiled admin page and its assets.
